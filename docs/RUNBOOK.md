# 生产发布与应急回滚手册（Operations Runbook）

## 库存对账健康度

看板顶部的“实时库存对账”徽章根据当前库存与启动时 SKU 总量基线（可用 + 预占）显示健康度；API 无法访问或缺少基线时显示“未知”。`inventory_reconciliation_mismatch_total` 记录每个 SKU 首次进入不一致状态的次数，是累计计数，不代表当前未解决差异数；修复后当前状态可恢复健康，但历史计数不会归零。

风控撤单回补耗时以 `inventory_risk_restock_duration_ms_sum` 和 `inventory_risk_restock_duration_count` 记录，平均耗时为两者相除；样本数为 0 时没有可用的耗时样本。发布时同时观察取消/回补成功率、重试、DLQ 与该耗时，按 10% → 50% → 100% 灰度推进；出现对账差异、DLQ 增长或耗时超过既定 SLA 时停止放量。

## 对账不一致核查与回滚

1. 暂停继续放量，记录发生时间、SKU、订单及当前指标快照；确认 `inventory_reconciliation_mismatch_total` 的增长时间，并检查对应订单状态、库存审计记录和 `inventory.restock.dlq` 消息。
2. 将每个 SKU 的可用库存与预占库存合计，与看板当前对账结果、权威库存台账及已确认订单/取消事件逐笔核对。检查是否存在重复消费、漏消费、失败重试或人工库存调整；不要通过直接覆盖库存数来消除差异。
3. 若存在 DLQ 消息，先确认原事件是否已回补、核对其 `idempotencyKey`，并在修复失败原因后通过受控重放恢复。不得绕过去重保护，也不得对未核实的消息批量重放。
4. 若差异持续扩大或无法确认库存安全，按部署环境已配置且验证过的实时回补降级开关（Feature Flag）暂停新实时投递，记录并排空或核实在途消费者，保留取消事件与审计记录，再切回经验证的准实时跑批回补流程。若没有已验证的开关或跑批流程，不要假设其存在；先停止放量并按应急流程协调安全暂停。切换前确认跑批与实时消费者共享幂等键，避免重复释放库存。
5. 回滚后逐 SKU 再次对账，并验证订单取消仍被完整记录、库存总量守恒且 DLQ 已有处置结果。只有差异查明并修复、监控稳定后，才重新启用实时回补并从低比例灰度开始。
